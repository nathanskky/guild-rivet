# Open question: Content-Security-Policy and the page layout

**Status:** open, not designed. Raised by the whole-branch review of the page layout work.
**Affects:** `Guild\Rivet\Component\Page\Page`, `Guild\Rivet\Page\RivetAssets`

## The problem

`rvt_page` emits Rivet's assets as five tags. Four carry a `src`/`href`; one is inline:

```html
<link rel="stylesheet" href="…/rivet.min.css">            <!-- head -->
<link rel="stylesheet" href="…/rivet-icon-element.css">   <!-- head -->
<script src="…/rivet.min.js"></script>                    <!-- end of body -->
<script>Rivet.init()</script>                             <!-- end of body, INLINE -->
<script type="module" src="…/rivet-icons.js"></script>    <!-- end of body -->
```

Under a Content-Security-Policy with a strict `script-src` — no `'unsafe-inline'` — the
inline `Rivet.init()` call is refused by the browser. Rivet does nothing until `init()`
runs, so the page renders with every interactive component dead: dialogs will not open,
disclosures will not expand, tabs will not switch. Nothing errors server-side; the page
simply arrives inert.

The four external tags are a smaller problem: an application can allowlist the CDN host,
or self-host through `RivetAssets`' `cssHref`/`jsSrc` overrides. **The inline script has
no such escape.**

## What an affected application has to do today

Set `enabled: false` on `RivetAssets` and hand-write the whole asset block — including
its own nonced `Rivet.init()`. That works, but it gives up the convenience the layout
exists to provide, and it means the one thing most likely to drift (which Rivet version
a page loads) moves back out of `RivetAssets` and into every application's template.

This is the workaround the README should describe if the question stays open for long.

## Why this is not a defect

`rvt_page` was specified without CSP in scope, and the behaviour is correct for an
application that has no strict policy — which is most of them today. This is a gap in
capability, not a bug in what was built.

It is worth taking seriously anyway: IU applications handling student data are exactly
the population most likely to be told to adopt a strict CSP.

## Options, unevaluated

1. **A `nonce` on the asset configuration.** Applied to all three `<script>` tags, and
   possibly the two `<link>` tags if `style-src` is also strict. Smallest change, keeps
   the layout's convenience intact.
2. **Make the inline init optional.** A flag that suppresses just the
   `<script>Rivet.init()</script>` line, leaving the external tags in place, so an
   application supplies its own nonced init. Smaller surface than option 1, but leaves
   the application to remember that Rivet does nothing without `init()`.
3. **Never emit an inline script.** Ship or reference a tiny external file that calls
   `Rivet.init()`, so every emitted tag has a `src` and a host allowlist is sufficient.
   Removes the problem rather than parameterising it, at the cost of an extra request and
   a file this package would have to host or point at.
4. **Document the opt-out and stop there.** Treat a strict CSP as a case where an
   application writes its own asset block, and make sure the README says so plainly.

## The constraint that will decide the shape

**A nonce must be unique per HTTP response and unguessable.** That rules out holding it
anywhere application-scoped.

`PageDefaults` is the natural-looking home and is probably the wrong one: it is
documented as configured once per application. In the current Guild framework that
happens to be per-request, because the container is rebuilt for every request — so a
nonce on `PageDefaults` would be accidentally correct there, and silently reused across
every response under a worker runtime such as FrankenPHP or RoadRunner. A reused nonce is
worse than no nonce: it looks like protection while defeating it.

`RenderContext` already carries per-render state (the id generator), and `Renderer::reset()`
already marks the start of a render. That is the more likely home, and it makes the
per-response lifetime structural rather than a rule someone has to remember.

Whichever option is chosen, that lifetime question needs settling first.

## Questions to answer before designing

- Do any IU applications this library targets actually run a strict `script-src` today,
  or is this anticipatory? The answer changes how much machinery is justified.
- Is `style-src` strict in those policies too, or only `script-src`? That decides whether
  the `<link>` tags need the nonce as well.
- Does any target deployment use a worker runtime (FrankenPHP, RoadRunner), or is every
  one of them process-per-request? This decides whether the lifetime hazard above is
  theoretical or live.
- Would `strict-dynamic` be in play? It changes what a nonced loader script may go on to
  load, and Rivet's own script loads nothing further, so probably not — worth confirming.
